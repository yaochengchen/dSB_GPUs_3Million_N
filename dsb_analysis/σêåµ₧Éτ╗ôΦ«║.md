# all_result.7z 分析（v5 + v5_supp，Grace 稠密 scaling 尚未到）

数据：GH200 单卡，CUDA 13.2，SB 2.0.0 用对齐调度（`discrete-matched`），dt 按实例自动选，reduction 全关。
K2000 / G-set B=512，QPLIB B 按 n 取 256–2048，K ∈ {200,400,800,1600,3200}，每格 50 个 seed。
全部数字由 `run_all.py` 从 raw 行重算，见 `out/summary.md`。

## 1. 命题 1 的实证比预想的还强：TF32 也精确

K=3200 时逐 seed 比较最终 cut（`out/tables/trajectory_identity.csv`，图 `figS_trajectory_identity`）：

- K2000 与 16 个 G-set 实例上，**gemm-TF32、gemm-FP32(no TF32)、gemm-INT8、bit、block 五条路径 50/50 seed 完全相同**；QPLIB 的 15 个三元实例同样。
- 不同的只有 gemm-FP16（K2000 上 21/50 相同）、csr-row/csr-block（26/50）和 SB。
- 4 个非三元 QPLIB 实例（5721/5725/5755/5875）上所有低精度路径都不同，符合预期。

对稿子的影响：
1. §5.6 表里 "gemm TF32 → Exact on ternary: no" 要改成 yes。原因：TF32 操作数 ±1 和 0 精确，累加是 FP32，整数和 |A| ≤ n < 2^24 精确，**与累加顺序无关**。同理 "累加顺序不同" 不能解释 FP16 和 CSR 的分歧——整数在 FP32 里怎么加都精确。FP16 不同大概率是 J 事先乘了 ξ（或 cuBLAS 用了 FP16 输出），CSR 不同要查 update 内核的运算顺序 / RNG。这两处 §3.3、§5.4、§5.5 的解释都要改。
2. block（fused）也在精确组里，正文只说了 TF32/INT8/bit 三条。

## 2. K2000（n=2000，完全图）

- 所有路径时间严格 ∝ K（图 1A），每步时间在 200–3200 步间波动 <3%。
- wall 加速只有 3–4×：gemm 路径每次 solve 有 30–90 ms 的 setup/handle/graph 开销（harness 每个 repeat 重建 solver）。**这是 wall 数字最大的失分项**，和之前 v5 分析一致。
- 同步数下质量明显好于 SB：3200 步 34/50 vs 9/50，中位 33337 vs 33308。
- 成功率随 K 陡升（800 步 1/50 → 1600 步 11/50 → 3200 步 34/50，图 4C），TTS99 最优在 3200 步：INT8 0.26 s、FP16 0.20 s，SB 13 s。

## 3. G-set（16 个实例，n=800–20000）

- 最快路径（integration）：csr-block 8 个（平均度 ≤4 和 G48）、csr-row 2 个（G55、G60，度 5）、gemm FP16 6 个（度 12–48）。**auto 一次都没选到 csr-block**（它的判据里 csr-block 只在 B≥1024 才启用），实际 K=3200 时 auto 比最快路径慢 1–3.4×（G1 上 bit 21.8 µs vs gemm FP16 6.4 µs）。
- integration 加速 13.5×–137×（中位 27×）；wall 加速 4.6×–115×（中位 22×）。gemm-FP16 实例 wall 掉得最多（G22：13.5→4.6×），还是 setup 问题。
- 解质量：中位 gap dsb 优于 SB 10 个、平 5 个、劣 1 个（G64：0.88% vs 0.78%）。n ≥ 5000 的 10 个实例 50 次里没有一次到 best-known，gap 0.18–1.3%；SB 同样 0 次。
- B 扫描（G55–G81，512→8192，图 4A/B）：时间严格 ∝ B（compute-bound），中位 gap 只降 0.03–0.09 个百分点，**best-of-50 也没碰到 best-known**。所以大 G-set 上 TTS99 依然无穷，靠加 B 解决不了；论文里这些实例只能报 gap，不能报 TTS。
- 66 实例 library 口径（图 7）：csr-row 比 SB 库默认参数快 4.7–77×（中位 10.8×）；800 步内 SB 库默认 pump 到不了 1，gap 在 64/66 个实例上更差，只在 3 个实例到过 best-known（dsb 30 个）。**这一组说明必须用对齐调度做主对比**，正好给 §7.6 的表右列填数：SB 库默认 dt=0.1、pump=min(k/1000,1)、初值 uniform(−1,1)。

## 4. QPLIB（19 个实例，n=200–1225）

- csr-block 17/19 最快，gemm FP16 2 个（5721、5875，稠密实数 J）。integration 加速 17.6–86×（中位 58×），wall 9–59×（中位 42×）。
- auto 在 QPLIB 上选的是 bit（三元实例）或 gemm，比最快的 csr-block 慢 2–9×（中位 6×）；这是 auto 判据最该改的地方。
- SB 每步 163–175 µs 平地板，与 n、B 无关：**这一族的加速全部是 launch-bound 区间的收益**，正文要明说。
- 质量：18/19 实例至少一次到 best-known（SB 15/19）；3838 (48 vs 17)、3850 (43 vs 22)、3642 (50 vs 40) 成功次数差距大；3650 和 5725 上中位 gap 略输（0.1% 级别，成功数 25 vs 26、3 vs 0）。
- 补齐的 `gemm:fp32:notf32` 列：QPLIB 上 no-TF32 比 TF32 慢 1.3×（中位），G-set 上 5×，K2000 4×——小 n 时 GEMM 不是瓶颈，所以 TF32 的贡献在 QPLIB 上几乎没有。

## 5. 大稀疏 scaling（d=100 二部图，csr-row）

每个 nonzero 每步 0.152–0.156 ns，0.65×10¹² 更新/s，n 从 1 万到 20 万完全恒定；n=20 万只用 561 MB。SB 在 1/2/5 万上分别慢 8.1/14.1/33.2×，10 万起稠密 J 放不下。全部 10/10 命中平凡最优，只能当吞吐实验。

## 6. 稠密 scaling（HBM 部分）

- n ≥ 8 万时 dsb-gpu 与 torch 都到 4.2–4.3 TB/s（HBM3e 峰值的 86–88%），fp16 完全打平；fp32 列的 2–4× 是 TF32 vs FP32。
- OOM 边界（0.85 HBM 预算）：fp32 20 万，fp16 30 万，两边一样。
- **Grace 目录只有表头**，`grace_bytes>0` 的点一个都没有。等你那边跑完，把 `results/dense_scaling_v5_supp_grace/` 放进 root 重跑 `run_all.py` 即可，图 8 会自动把 Grace 点圈出来。

## 7. 对论文文本的具体改动建议（本次只插了图，没改正文数字）

1. **表 3/7/11 及 §8.1、§8.6–8.8 的数字仍是 v4（B=200、未对齐 baseline）**。`out/tables/tab_k2000_K3200.tex`、`tab_k2000_steps.tex` 是 v5 B=512 的对应表，可以直接换；换表后 §8.6/§8.7 里 17.5×、102.8×、138.9× 等文字数字要同步改（v5 下 K2000 等工作量加速是 13.6×，等质量比较要重算）。
2. §5.6 表 "TF32: no" → yes；§3.3/§5.4/§5.5 关于"累加顺序"的解释要改（见第 1 节）。
3. §8.1 K2000 段落里 `S_max=[ ]`、`R_max=[ ]` 可填 232,448 B 和 8。
4. §8.8 "P0/G1 at every budget below one" 与数据矛盾（见上一轮），且本轮 reduction 没跑，§8.2 表 8 / 图 2 仍然空。标题里的 Hamiltonian Reduction 要么补约简表，要么改题。
5. auto 选择器建议改成：平均度 ≤ 4.5 → csr-block（不限 B），5–8 → csr-row，≥ 12 或非三元 → gemm FP16；bit 只在 gemm 放不下时选。按现有数据这样能在 G-set 上多拿 1.5–2×。
6. 把 setup（cuBLAS handle / graph instantiate / bit 打包）提到 repeat 循环外，wall 加速能从 4× 回到 ~13×（K2000）。
